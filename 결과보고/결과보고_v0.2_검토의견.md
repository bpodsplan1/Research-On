## 3. 수치 검증 결과

### 3-1. 슬라이드 21 — "100개 기사 중 중복 건 제거 후 20개 제안" → **수정 필요**

실제 워크플로우(`뉴스 크롤링 1단계`) 코드를 직접 열어서 확인했습니다.

- Serper·Naver News·Naver Web 원본 수집 → URL/제목 유사도 중복 제거 → 규칙 기반 1차 점수화 → **점수 상위 30개**를 "후보"로 압축 (`candidate_max || 30`, 코드에 30으로 명시)
- 이 30개를 AI(Gemini)가 재평가 → **최종 20개**를 사용자에게 제안 (`final_max || 20`)

즉 코드상 고정된 숫자는 **"100개"가 아니라 "30개"**입니다. "100개"라는 숫자는 코드 어디에도 없어서, 아마 자료 취합 중 다른 맥락(다른 워크플로우이거나 어림값)이 섞여 들어간 것 같습니다.

**제안 문구**: "원본 자료 수집 → 중복 제거 → **점수 상위 30개 후보 압축** → AI 재평가로 **최종 20개 제안**"

(참고: 원본 수집 건수 자체는 검색어 개수·검색 결과 유무에 따라 매번 달라지는 값이라 코드에 고정돼 있지 않습니다. "실제로 몇 건 정도 모이는지"는 n8n 실행 로그(`original_count` 필드)를 몇 번 확인해서 평균값을 넣으시는 게 정확합니다.)

### 3-2. 슬라이드 20 — "100개의 핵심 키워드" → **정확합니다**

어제·오늘 세션에서 키워드 체계를 112개 → 100개로 정리한 결과와 정확히 일치합니다. 그대로 두시면 됩니다.

### 3-3. 슬라이드 8 — T/F 운영 계획 주차 표기 확인 필요

Week 1(4/22, 하루)부터 Week 14~15(7/21~7/28)까지 표기되어 있는데, 이전 "운영계획 변경(案)" 문서에서는 전체 기간을 "14주"로 표현했었습니다. Week 1을 킥오프 하루짜리 반주로 셀지, 정식 1주차로 셀지에 따라 "14주"와 "15주차 표기"가 서로 다른 셈법이 되니, 다른 자료(예: 목차나 별도 요약 문구)에 "14주"라는 표현이 또 나온다면 이 슬라이드의 "Week 15"와 숫자가 안 맞아 보일 수 있어 확인을 권합니다.

## 5. 슬라이드 25 — 워크플로우별 API 사용량

⚠️ **먼저 짚어야 할 점**: Serper·Naver·Tavily는 "토큰"이 아니라 **호출 1회(요청/크레딧) 단위**로 과금됩니다. "토큰"이라는 표현은 LLM(Gemini)에만 해당하는 개념이라, 슬라이드 제목을 "API 토큰"보다는 **"API 호출량"** 정도로 바꾸고, LLM은 토큰 단위·나머지는 호출 단위로 구분해서 표를 나누는 걸 제안합니다.

아래 수치는 각 워크플로우의 n8n 코드를 직접 읽어서 계산한 **구조적으로 확정된 값**(쿼리 개수·페이지 수 등 코드에 하드코딩된 값 기준)입니다. 다만 Gemini 토큰량은 프롬프트 실측이 아닌 **글자 수 기반 추정치**라 ±30% 오차가 있을 수 있고, 아래 무료 제공량은 제 지식 기준이라 **발표 전 각 서비스 대시보드에서 반드시 재확인**해주세요.

### 5-1. 리서치 허브 — 키워드 검색 1회 실행 (뉴스 크롤링 1단계)

| API | 호출 횟수 (1회 실행 기준) | 근거 |
|---|---|---|
| Serper (구글 검색) | 최대 16회 | 한/영 검색어 최대 8개 × 페이지 2장(`SERPER_PAGES=2`, `num:10`) |
| Naver 뉴스 검색 | 최대 5회 | 검색어 최대 5개, 1회당 30건 조회 |
| Naver 웹문서 검색 | 최대 3회 | 검색어 상위 3개만, 1회당 20건 조회 |
| Gemini (검색어 생성) | 1회 | 입력 약 800~1,200자 → 약 400~600 토큰 / 출력 약 150~250 토큰 |
| Gemini (자료 30건 재평가) | 1회 | 후보 30건 title+요약 포함 → 입력 약 3,500~4,500 토큰 / 출력 약 1,500~2,000 토큰 |

**검색 API 호출 합계: 최대 24회** (Serper 16 + Naver 8) · **Gemini 토큰 합계(추정): 입력 약 4,300~5,700 / 출력 약 1,650~2,250**

### 5-2. 리서치 허브 — AI 인사이트 리포트 1건 생성 (뉴스 크롤링 2단계, 자료 선택 후 "인사이트 도출")

| API | 호출 횟수 | 근거 |
|---|---|---|
| Tavily Extract | 1회 호출 (최대 10개 URL 동시 추출) | "최대 10건까지만 분석 반영" 코드 제한 — Tavily는 보통 URL 1개당 1크레딧 소모 방식이라 **실질 크레딧 소모는 최대 10** |
| Gemini (종합 리포트 생성) | 1회 | 원문 10건 본문 + 회사 맥락(808자) → 입력 약 6,000~8,000 토큰 / 출력 약 1,000~1,500 토큰 |

**검색 결과 화면에서 "인사이트 도출"까지 이어서 누르면(5-1 + 5-2 합산)**: Serper 16 + Naver 8 + Tavily 10 크레딧, Gemini 입력 약 1만~1만3천 토큰 / 출력 약 2,700~3,800 토큰

### 5-3. 주간 뉴스레터 자동 발송 (뉴스레터 1단계, 주 1회 실행)

Supabase `newsletter_keywords` 테이블 실제 데이터 기준(CLIENT_WATCH 12개 · BUSINESS_WORK 20개 · PEOPLE_CULTURE 10개, 총 42개 키워드):

| 구간 | Serper | Naver 뉴스 | 비고 |
|---|---|---|---|
| CLIENT_WATCH (12개 키워드) | 12회 | 12회 | 키워드당 1+1 |
| BUSINESS_WORK (20개 키워드) | 20회 | 20회 | 키워드당 1+1 |
| PEOPLE_CULTURE (후보 최대 8개) | 0~8회 (조건부) | 8회 | Naver에서 못 찾은 후보만 SNS 보완검색 |
| **합계** | **32~40회** | **40회** | |

Gemini 호출은 3개 구간 각각 최소 1회(후보 평가/분석) + PEOPLE_CULTURE는 메일 후보 추출용 1회 추가 → **Gemini 호출 4회/주**, 토큰 합계(추정) 입력 약 8,000~12,000 / 출력 약 2,000~3,000 (구간별 후보 개수에 따라 변동)

### 5-4. 클라이언트 동향 수집 (매일 1회 자동 실행)

| API | 호출 횟수 |
|---|---|
| Serper | 1회 |
| Naver 뉴스 | 1회 |
| Gemini (동일사건 클러스터링) | 1회 (입력 약 1,500~2,500 토큰 / 출력 약 300~500 토큰) |

### 5-5. 무료 제공량 대비 (⚠️ 반드시 재확인 필요)

| API | 무료 제공량(제 지식 기준, 검증 필요) | 참고 |
|---|---|---|
| Serper.dev | 가입 시 1회성 2,500크레딧 무료 (월 정기 제공 아님) | 이후 종량제(예: 5만 건당 $50 수준) |
| Naver 검색 오픈API | 애플리케이션당 1일 25,000회 무료 | 매일 자정 리셋 |
| Tavily | 월 1,000크레딧 무료 (Search 1건=1크레딧, Extract는 URL당 소모) | 월 정기 리셋 |
| Google Gemini API (Flash-Lite급) | 무료 티어는 분당/일당 요청수(RPM/RPD) + 분당 토큰(TPM) 한도 방식 — 토큰 자체를 "무료 개수"로 단순 비교하기보다 "하루 몇 번 호출 가능한지"로 보는 게 더 정확 | 모델·계정 등급에 따라 다름 |

이 표를 기준으로 보면, **하루 몇 번의 리서치 검색이 이뤄지는지**(Naver 일 25,000회 무료 한도 대비)와 **Serper 무료 크레딧이 언제 소진될지**(1회 실행당 최대 16회 소모 → 2,500크레딧이면 약 150회 정도의 리서치 실행 후 소진)를 같이 보여주면 "확대 시 유료 전환이 언제 필요한지"를 설득력 있게 전달할 수 있을 것 같습니다.

## 6. 확인이 필요한 부분 (제가 계산할 수 없는 것들)

- **슬라이드 21의 "7.5초"/"13.4초"** — 말씀하신 대로 n8n 실행(Execution) 로그의 실제 소요시간을 평균 내야 하는 값이라 그대로 두었습니다.
- **뉴스레터 누적 발행 횟수** — 계속 늘어나는 값이라 발표 직전 Supabase에서 재확인 권장.
- **Gemini 실제 토큰 소모량** — n8n 각 실행의 "Google Gemini" 노드 출력 데이터에 `usageMetadata`(promptTokenCount/candidatesTokenCount)가 실제로 찍혀 있을 가능성이 높습니다. 실행 로그 몇 건만 열어봐도 제 추정치보다 훨씬 정확한 실측값을 바로 얻으실 수 있습니다.
